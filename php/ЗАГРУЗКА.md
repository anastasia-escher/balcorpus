# Как загружать корпус на сервер

Простыми словами: что один раз настроить, и что делать каждый раз, когда
приходит новый текст.

> **Важно:** PHP-часть ещё не написана. Это описание того, что мы сделаем, —
> и одновременно спецификация, по которой я буду писать код. Команды ниже
> заработают, когда файлы появятся.

Сервер: `languagesofthebalkans.whp.uzh.ch`
Заходить: `ssh languagesofthebalkan_hexru0kbt4j@130.60.247.23`

---

## Зачем вообще PHP

Хостинг у нас только один — Plesk, и на нём есть только PHP. Поэтому Django
остаётся локальным инструментом: он проверяет и импортирует файлы
лингвистов и выписывает готовые CSV. А на сервере работает маленький
PHP-бэкенд без фреймворков — в том же духе, что старый проект
`balkan_corpora/php/`, но с безопасными запросами к базе.

PHP-код повторяет устройство Django-приложения `core`, чтобы одно легко было
сверить с другим:

| Django | PHP |
|---|---|
| `models.py` | `private/sql/schema.sql` |
| запросы ORM | `private/sql/*.php` — все SQL-запросы, только здесь |
| `views.py` | `private/views/` — разобрать запрос, проверить лимиты, ответить |
| `serializers.py` | `private/serializers/` — собрать JSON в том виде, какой ждёт сайт |
| `processing/` | `private/processing/` — поиск, контекст, xlsx |
| команды импорта | `private/upload/` — загрузчик CSV в базу |

---

## Что где лежит на сервере

Две папки рядом друг с другом. Разница между ними важная:

```
httpdocs/          ← это видно из интернета
private/           ← это из интернета не видно
```

Всё, что не должно быть доступно посторонним — пароль от базы, секрет
загрузчика, данные для загрузки, сам код бэкенда — лежит в `private/`.
Наружу торчат только маленькие файлы-«входы»: каждый из них в пару строк
подключает нужный файл из `private/views/`.

Обратите внимание: файла, который отдавал бы предложения текста подряд, здесь
нет и быть не должно. У корпуса нет права публиковать тексты целиком, поэтому
наружу выходят только поиск и короткое окно вокруг находки. В данных на
сервере тексты лежат полностью, но добраться до них можно лишь через эти
ответы — так же, как на Django-версии, где списки `/api/v1/sentences/` и
`/api/v1/tokens/` закрыты намеренно. Если когда-нибудь понадобится
показывать текст целиком, это решение принимается отдельно, а не
добавлением ещё одного `index.php`.

Полная картина:

```
httpdocs/
  index.html                         сайт (сборка Nuxt)
  _nuxt/                             его стили и скрипты
  texts/index.html                   страница со списком текстов
  api/v1/
    texts/index.php                  список текстов (?q= — поиск по нему)
    texts/coverage/index.php         сколько текстов размечено из скольких
    tokens/search/index.php          поиск
    tokens/search/xlsx/index.php     весь результат поиска одним .xlsx
    sentences/context/index.php      контекст вокруг находки
  upload/index.php                   страница загрузчика (под секретом)

private/
  config.php                         доступы к базе и секрет — ТОЛЬКО здесь
  db.php                             подключение к базе
  sql/
    schema.sql                       создание таблиц
    ...                              SQL-запросы
  views/                             по файлу на каждый адрес API
  serializers/                       сборка JSON-ответов
  processing/                        логика поиска, контекста, xlsx
  upload/                            загрузчик CSV в базу
  data/                              обычно ПУСТАЯ, см. ниже
    speakers.csv
    texts.csv
    text_authors.csv
    sentences/<text_id>.csv
    tokens/<text_id>.csv
```

Почему адрес `httpdocs/api/v1/texts/index.php` отвечает на `/api/v1/texts/`:
если в папке лежит файл `index.php`, сервер отдаёт его, когда запрашивают саму
папку. Поэтому никаких дополнительных настроек не нужно, и адреса остаются
ровно такими, какие уже ждёт сайт.

## Ограничения публичного API

Те же, что на Django-версии, — чтобы поведение сайта не зависело от того, какой
бэкенд за ним стоит:

| Что | Предел | Ответ, если превышен |
|---|---|---|
| запросов к API с одного IP | 60 в минуту | 429 |
| выгрузок `.xlsx` с одного IP | 5 в минуту (сверх общих 60) | 429 |
| длина любого поля поиска | 100 символов | 400 |
| тег `pos` только из `?` и `*` (`*`, `???*`) | не считается словом; без другого поля — отказ | 400, как пустой поиск |
| строк в выгрузке `.xlsx` | 10 000 | 400, «сузьте поиск» |
| результатов на странице поиска | 50 по умолчанию, не больше 100 | — |

`.xlsx` собирается встроенным в PHP `ZipArchive`, без сторонних библиотек.
Текст в ячейках всегда записывается как текст, никогда как формула — даже
если начинается с `=`.

## Один раз: первоначальная настройка

### 1. Создать базу

В панели Plesk: **Базы данных → Добавить базу данных**. Имя любое, пользователя
Plesk создаст сам с приставкой `whp_`, пароль — кнопкой **Generate**.
Пароль сразу сохранить, второй раз его не покажут.

### 2. Создать папки на сервере

Зайти по SSH и выполнить:

```
mkdir -p private/data/sentences private/data/tokens
```

Папки под `httpdocs/` создавать руками не нужно — они приедут вместе с
файлами на шаге 4.

### 3. Записать доступы к базе и секрет

Создать файл `private/config.php` с данными из шага 1 и **секретом
загрузчика** — длинной случайной строкой. Получить её можно так:

```
php -r 'echo bin2hex(random_bytes(32)), "\n";'
```

(или любым генератором паролей, не короче 40 символов). Секрет, как и пароль
от базы, живёт только здесь — ни в других файлах, ни в git, ни в переписке.
Себе его сохранить в менеджер паролей: он понадобится при каждой загрузке.

### 4. Залить PHP-файлы

С локального компьютера, из папки проекта:

```
scp -r php/private/* languagesofthebalkan_hexru0kbt4j@130.60.247.23:private/
scp -r php/httpdocs/* languagesofthebalkan_hexru0kbt4j@130.60.247.23:httpdocs/
```

### 5. Создать таблицы

По SSH:

```
mysql -h mariadb.uzh.ch -P 3310 -u whp_ПОЛЬЗОВАТЕЛЬ -p ИМЯ_БАЗЫ < private/sql/schema.sql
```

Если команды `mysql` на сервере нет — то же самое через **phpMyAdmin** в
панели: открыть базу, вкладка «Импорт», выбрать файл `schema.sql`.

### 6. Собрать и залить сайт

Локально:

```
cd ui/app
yarn install --frozen-lockfile
NUXT_PUBLIC_API_BASE_URL= yarn build
scp -r .output/public/* languagesofthebalkan_hexru0kbt4j@130.60.247.23:httpdocs/
```

Пустой адрес значит «тот же сервер, откуда открыт сайт»: сайт и API лежат
на одном домене, поэтому сайт спрашивает просто `/api/v1/...`. Пустое
значение в команде написано нарочно — чтобы адрес из локальной разработки
(`localhost`), если он остался в терминале, не попал в сборку.

## Каждый раз: новый текст приходит от лингвистов

### 1. Локально: проверить и импортировать

Сначала — одна строка про новый текст в `data/input/metadata_texts/texts.xlsx`
(и про нового человека в `metadata_speakers/speakers.xlsx`, если он новый),
по образцу соседних строк, и импорт этой таблицы — см. `data/README.md`.

Потом файл от лингвистов **как есть**, ничего не переделывая, кладём в
`data/input/annotations/` и запускаем:

```
docker compose exec api python manage.py upload_transcription /data/input/annotations/ИМЯ_ФАЙЛА.xlsx
```

Команда сама проверит файл, найдёт текст по названию и людей по именам,
импортирует его и запишет готовые CSV в `data/php_ready/`. Если в файле
ошибки — ничего не импортируется и все проблемы выводятся списком. Если
название есть у двух текстов, команда перечислит их `text_id`, и нужный
указывается так: `... upload_transcription ФАЙЛ.xlsx --text ИДЕНТИФИКАТОР`.

### 2. Положить файлы на сервер

Для нового текста нужны ровно два файла:

```
scp data/php_ready/sentences/ИМЯ_ТЕКСТА.csv languagesofthebalkan_hexru0kbt4j@130.60.247.23:private/data/sentences/
scp data/php_ready/tokens/ИМЯ_ТЕКСТА.csv languagesofthebalkan_hexru0kbt4j@130.60.247.23:private/data/tokens/
```

### 3. Запустить загрузчик в браузере

Открыть `https://languagesofthebalkans.whp.uzh.ch/upload/`. Там одно поле —
вставить секрет из `config.php` и нажать «Загрузить». Страница покажет, что
загружено: сколько людей, текстов, предложений и токенов, и ошибки, если
были.

### 4. Очистить `private/data/`

```
ssh languagesofthebalkan_hexru0kbt4j@130.60.247.23 'rm -f private/data/*.csv private/data/sentences/*.csv private/data/tokens/*.csv'
```

## Как загрузчик защищён

Загрузчик открыт из интернета, поэтому у него две защиты, и обе нужны:

1. **Секрет.** Без правильного секрета страница ничего не делает. Секрет
   отправляется из формы (POST), а не в адресе, — поэтому он не попадает ни в
   историю браузера, ни в логи сервера. Открыть страницу (GET) можно, но это
   только форма.

2. **Пустая папка.** Загрузчик берёт данные только из `private/data/` и
   загружает ровно то, что там лежит. Папка пуста — ему нечего делать, даже
   с правильным секретом. Файлы кладём туда только на время загрузки и сразу
   после неё удаляем (шаг 4 выше).

Поэтому даже если секрет когда-нибудь утечёт, вреда он не сделает, пока папка
пуста, а новый секрет — это одна строка в `config.php`.

## Когда меняются метаданные

Если правились таблицы говорящих или текстов — файлов три, и разметку
текстов трогать не нужно:

```
scp data/php_ready/speakers.csv data/php_ready/texts.csv data/php_ready/text_authors.csv \
    languagesofthebalkan_hexru0kbt4j@130.60.247.23:private/data/
```

Дальше — так же: загрузчик в браузере, потом очистить `private/data/`.

Можно класть метаданные и тексты вместе, за один раз. Загрузчик сам
соблюдает порядок: сначала люди, потом тексты, потом авторы, потом разметка —
потому что каждое следующее ссылается на предыдущее.

## Можно ли залить файл второй раз

Да, сколько угодно раз. В этом весь смысл: заметили ошибку в старых данных,
исправили исходный xlsx, импортировали локально, залили заново. Загрузчик
рассчитан на повторную загрузку, а не только на первую.

Но ведёт он себя по-разному для разных файлов — и ровно так же, как Python
ведёт себя локально. Это не мелочь: если поведение разойдётся, база на сервере
тихо перестанет совпадать с вашей.

| Файл | Что делает загрузчик | Почему так |
|---|---|---|
| `speakers.csv` | обновляет тех, кто уже есть, добавляет новых | исправление в данных человека должно дойти до сервера |
| `texts.csv` | то же самое | |
| `text_authors.csv` | стирает **все** связи и записывает файл целиком, в одной транзакции: если в файле ошибка, старые связи остаются | автора могли заменить или убрать совсем; у текста без автора в файле просто нет строк, а стирание по одним текстам из файла его старого автора никогда бы не убрало |
| `sentences/<текст>.csv` | стирает **всю** разметку этого текста и пишет заново | |
| `tokens/<текст>.csv` | то же самое | |

**Скрытые данные людей — колонка `show_metadata`.** В `speakers.csv` она
равна `1` (показывать) или `0` (скрывать). Данные в базу загружаются
**всегда целиком**, а скрывает их уже ответ API: у человека с `0` в
`/api/v1/texts/` остаются только `speaker_id`, `full_name`, `gender`, `l1`,
`l2`, `l3`, остальные поля отдаются как `null` — так же, как в Django
(`SpeakerSerializer`). Поле `religion` лежит в базе, но API не отдаёт его
никогда и никому, независимо от флага. Поэтому флаг можно переключить прямо на сервере, в
phpMyAdmin, одной ячейкой — и в обе стороны. Но следующая загрузка
`--metadata` снова возьмёт значение из файла, так что постоянное решение
вносится в колонку `show_metadata` исходного `speakers.xlsx` (пусто = да).

**Защита от дублей — как `update_or_create` в Django.** Для людей и текстов
загрузчик сначала смотрит, есть ли уже запись с таким `speaker_id` /
`text_id`: есть — обновляет её поля, нет — создаёт новую. Второй записи с тем
же идентификатором не появится никогда. В PHP это один запрос
`INSERT ... ON DUPLICATE KEY UPDATE`, а сторожит его уникальный ключ в
таблице (`speaker_id` у людей, `text_id` у текстов), — то есть даже ошибка в
коде загрузчика не сможет записать дубль, база его не пустит.

Для разметки защита другая — стирание текста перед записью (объяснение ниже),
а подстраховка та же: уникальные ключи «текст + номер предложения» и
«предложение + номер токена», как `unique_together` в Django.

В отчёте загрузчик, как и Django, пишет, сколько записей **создано** и сколько
**обновлено**, — по нему видно, что повторная загрузка ничего не удвоила.

**Почему разметка стирается целиком, а не обновляется по строкам.**
Допустим, в тексте было 100 токенов, вы нашли два лишних и убрали их — стало
98. Если бы загрузчик просто обновлял строки, он обновил бы 98, а два лишних
остались бы в базе навсегда: в новом файле их нет, значит их никто не тронет,
и поиск продолжил бы их находить. Стирание целиком даёт ровно то, что в файле.

Каждый текст загружается целиком или не загружается вовсе: если в его файлах
ошибка, старая разметка этого текста остаётся как была. Другие тексты при
этом не затрагиваются — стирается только то, что относится к загружаемому
тексту.

**Что не удаляется никогда:** человек или текст, которых больше нет в
метаданных, из базы не пропадает. Так же ведёт себя Python. Удалять их
автоматически опасно — на них могут ссылаться предложения уже загруженных
текстов.

## Правила, чтобы ничего не сломать

1. **Файлы в `php_ready/` руками не правим.** Они создаются командой импорта.
   Исправлять нужно исходный xlsx и импортировать заново.

2. **Не заливаем пустой файл текста.** Загрузчик заменяет разметку текста
   содержимым файла, поэтому пустой файл её сотрёт. Команда экспорта такой
   файл не создаёт специально, но если он откуда-то взялся — не заливать.

3. **После загрузки `private/data/` снова пустая.** Это вторая половина
   защиты загрузчика.

4. **Пароль от базы и секрет — только в `private/config.php`.** Не в коде, не
   в git, не в переписке.

## Если что-то не работает

| Что видно | Где смотреть |
|---|---|
| Сайт открылся, но пустой, ничего не находит | адрес API при сборке — шаг 6 |
| «Connection refused» при загрузке | сервер не видит `mariadb.uzh.ch:3310` |
| Вместо букв «Ð¿Ð°Ð½Ð¾Ð²» | кодировка таблиц — должна быть `utf8mb4` |
| Поиск не находит слово с заглавной буквы | сравнение таблиц — должно быть `utf8mb4_unicode_ci` |
| 404 на `/api/v1/texts/` | файл лежит не как `api/v1/texts/index.php` |
| Загрузчик пишет «нечего загружать» | файлы не в `private/data/` или не в тех подпапках |
| Загрузчик обрывается на большом тексте | лимит времени PHP; загружать тексты по одному |
| 429 при поиске | сработал лимит запросов; подождать минуту |
